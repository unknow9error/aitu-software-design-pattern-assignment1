# Подготовка к защите

## Объяснение за 2 минуты

Продукт — учебный отчёт `Report`. У него есть заголовок, формат и готовое содержимое.
Секции можно добавлять постепенно: абзацами и списками.
`ReportBuilder` задаёт общие шаги и возвращает builder из каждого шага,
поэтому вызовы можно соединять в цепочку.

`AbstractReportBuilder` хранит состояние, проверяет входные данные и в `build()`
создаёт продукт. `MarkdownReportBuilder` и `HtmlReportBuilder` преобразуют секции
в разные представления: Markdown-разметку или полноценный HTML-документ.
Это не просто разные значения полей: структура и синтаксис результата различаются.

`ReportDirector` хранит один готовый рецепт учебного отчёта и работает с интерфейсом.
Клиент `Main` выбирает конкретный builder. Рецепт остаётся одинаковым для обоих
форматов. Без Director можно собрать собственный отчёт прямо в клиенте.

## Живая демонстрация

1. Выполнить `bash scripts/run.sh` и показать оба результата в терминале.
2. Открыть `output/study-report.html` в браузере, а `.md` — в Markdown preview.
3. Показать одинаковые вызовы Director с разными builders в `Main.java`.
4. Показать fluent-цепочку без Director в том же файле.
5. Выполнить `bash scripts/test.sh`: должно быть `PASS: 43 tests`.
6. Показать тест `missing sections`: вызов `title("Title").build()`
   выбрасывает `IllegalStateException` с объяснением причины.

## Вероятные вопросы

**Почему Builder, а не большой конструктор?**
У отчёта переменное количество секций. Цепочка шагов читается лучше конструктора
с вложенными списками и даёт один способ сборки для нескольких форматов.
Для маленького объекта из двух полей обычный конструктор был бы проще.

**Чем это отличается от Factory?**
Factory обычно выбирает и создаёт объект за одну операцию. Здесь клиент добавляет
части по шагам, а готовый продукт появляется при `build()`.

**Почему не одна функция render(format)?**
Это допустимая более простая альтернатива. Здесь отдельные builders изолируют
правила вывода; новый builder можно подключить к существующему Director.
Конкретная сериализация в конце сборки похожа на Strategy, а накопление состояния
через шаги и получение продукта реализуют Builder.

**Зачем абстрактный класс, если уже есть интерфейс?**
Интерфейс — контракт для клиента и Director. Абстрактный класс повторно использует
хранение секций, проверки и создание продукта. Иначе две реализации дублировали
бы этот код. Поддерживающие типы оставлены в одном пакете для простоты задания.

**Почему Report — record?**
Java record является классом с final-полями, конструктором, accessor-методами,
equals и hashCode. Все поля здесь неизменяемые — строки и enum — поэтому продукт
не меняется после сборки. У builder состояние, напротив, изменяемое.

**Что если вызвать build() дважды?**
Без новых шагов результаты равны. Сборка не очищает builder. Новые шаги влияют
только на следующий Report. Для каждого запуска Director создаётся новый builder.

**Где валидация?**
Шаги немедленно отклоняют пустые поля, null, переносы строк и пустые списки.
`build()` дополнительно проверяет полноту отчёта: заголовок и хотя бы одну секцию.
Ошибочный шаг не должен частично менять состояние; это проверяется тестом.

**Зачем экранирование?**
Строка `<script>` должна остаться текстом, а не стать HTML-тегом. Markdown также
экранируется, чтобы введённые `*`, `#` и ссылки не меняли структуру документа.

**Какие минусы решения?**
Классов больше, чем у одной функции; всё содержимое хранится в памяти; поля только
однострочные; builder не потокобезопасен; автоматического reset нет.
Добавление третьего формата потребует также нового значения `ReportFormat`.
